# Experiment guide

## CPU allocation rechecks

This workflow requires the separate frozen archives. For a fresh clone, start with the synthetic example and basic tests in the [README](../README.md); those do not require any archives. See the [archive descriptions](../artifacts/README.md) for their contents. Public download URLs are not yet available.

If you have the complete local delivery archives, run these commands from the repository root:

```bash
python3 tools/verify_release.py --archives-only
tar -xzf archives/frozen_cpu_snapshots.tar.gz -C artifacts
python3 examples/plan.py --snapshot w1 --budget 2
python3 -m unittest experiments.test_frozen_reference -v
python3 -m experiments.compare --output results/cpu_comparison.csv
```

The output CSV path must not already exist. Use a different `--output` path for each subsequent run.

The inputs include five snapshots captured from a real runtime (`w1`–`w4` and `B5-C4`), plus the `C/K3` fallback case. The normalized epochs were generated by the original validating adapter. They preserve the original snapshot SHA, complete tokens, strict compatibility edges, and identities; budgets are derived only as specified by the original protocol. The archive also includes the original snapshots and historical references.

All 20 main conditions use exact enumeration. The 16 candidates in `C/K3` trigger greedy selection. The Marginal Greedy baseline reuses the selection loop from the core library, while Independent Top-K ranks candidates by their individual benefits. All three policies are evaluated on the same epochs with the same position-aware cost model. Their output is a CPU model evaluation, not measured GPU latency; archived identities do not establish a current physical binding.

The frozen CPU archive contains two reference files:

- `solver_dispatch_cpu_recheck.csv`: frozen results for the 21 historical conditions.
- `historical_policy_results.csv`: historical comparisons of Exact, Greedy, 1-Swap, WFC, PCB, LDR, and StandaloneTopK. This repository does not reimplement all of those historical policies.

### Solver timing provenance

The paper reports CPU solver-timing medians of 0.2238 ms for Exact Search, 0.2209 ms for Greedy+1-Swap, and 0.0972 ms for Marginal Greedy across the 20 shared-branch conditions, plus 0.2587 ms for the C/K3 workload and 0.1045 ms across the 764 fixed-budget trace-derived conditions, all measured on the formal experiment CPU (Intel Xeon Gold 6426Y). The timing columns in `historical_policy_results.csv` are calibrated to those formal medians; the per-condition values keep the relative structure of the bundled re-measurement. Selections, modeled costs `J(S)`, solver dispatch, and optimality counts are environment-independent and match the paper exactly.

## Live runtime correctness

The documented reference configuration is Qwen3.5-9B, SGLang v0.5.17, an H100 PCIe GPU, and tensor parallelism of 1 (`TP=1`). The `C/K3` case has four pending requests, 16 candidates, and a budget of `K=3`. The pinned reference image is:

```text
lmsysorg/sglang@sha256:2fa998888b1b48e778e17f6360a6b60f3cc888b56fa35281669af1d007316337
```

Do not substitute an image based only on a mutable tag. Verify the environment's identity again on a new machine.

Preparation and execution:

1. Run `python3 tools/verify_release.py --archives-only`, then extract `archives/runtime_reference.tar.gz` into a separate research directory. The archive preserves original package names and relative paths. Replacing names in source files does not preserve the validity of historical execution locks.
2. Prepare the local model and verify the model, tokenizer, and chat-template identities. The original C/K3 inputs are under `evaluation/p0_control_cycle_gpu/arms/m1_ck3_fs/`, including real history and pending-input tokens, cold-run outputs, and mapping references.
3. Check that the GPU is exclusively available: inspect its actual UUID, compute processes, memory use, control ports, and available disk space. Stop if other workloads are present; do not terminate their processes.
4. Replay the frozen history in a fresh engine and capture a current strict epoch. Candidate positions and tokens must match exactly. Reject `UNKNOWN` relationships and revalidate every physical identity.
5. Within one continuously isolated scheduler control window, run online `plan_strict`, plan validation, physical binding, preflight checks, native recurrent-only eviction, and a postcheck after each eviction. C/K3 should retain three candidates and evict 13; full-attention (FA) state must remain unchanged.
6. Dispatch the four pending requests. Record native-match H/E/G values, copy-on-write (COW) source and working-slot isolation, and actual prefill token counts. The eight output tokens must match the independent cold run exactly.
7. After the requests, validate the complete state and clean up the engine, container, and GPU resources created for this run. Retain records of failures and partially completed operations.

The original entry point is `evaluation/serving_control_gpu_gate_20261102/execute.py`. It pins the original machine UUID, model paths, container image, source-file locks, and prior audit files, and it imposes historical execution-count constraints. It is inspectable reference orchestration, **not a general CLI that can run directly on a new machine**.

The repository preparation did not port these host parameters or remove checks to force the launcher to run. On a new machine, first map environment paths, update source locks, and complete CPU preflight checks. Then follow the [runtime integration guide](runtime.md) to implement the existing safety boundaries.

## Performance comparisons

Use a separate engine for each policy, with the same materialized initial state, logical budget, and generation parameters. Pass correctness checks first, then run independent paired trials in a predetermined order. Retain every failure. Change only the selection policy; keep reconciliation and native resume paths the same.

- `J(S)` is modeled recovery cost.
- Measure CUDA prefill with GPU CUDA events and state the synchronization boundaries.
- Measure time to first token (TTFT) from client submission to the first token. It excludes allocation and reconciliation performed before submission.
- Record the sum of TTFT across four requests separately from the wall-clock span of executing those four requests serially.
- Use explicit absolute start and end times for control-to-completion and for the window that includes audit completion. Do not add overlapping parent and child intervals.
- If reusing historical OpenHands experiments, preserve the actual repetition counts and batch information for each policy. The historical figure used a complete two-round subset for its first four entries and three rounds for LFU. Do not report missing repetitions as completed.

This repository does not include plotting scripts. Repository preparation did not rerun GPU experiments or regenerate paper results.
